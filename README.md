# Hackathon

A starter web project with a separated frontend and backend:

- **Backend** — FastAPI (Python) + PostgreSQL, in Docker, on http://127.0.0.1:5001
- **Frontend** — React (Vite) + Bootstrap 5.3, on http://127.0.0.1:3001

In production both are one container: the Dockerfile at the repo root builds
the React app and FastAPI serves it alongside the API (same origin).

## Structure

```
run-backend.sh      — start Postgres + backend in Docker (rebuilds only when needed)
run-frontend.sh     — start the frontend (npm install handled automatically)
new-migration.sh    — scaffold a DB migration file
migrate.sh          — apply/inspect/roll back migrations without restarting
docker-compose.yml  — local dev stack: Postgres + backend
Dockerfile          — deployment image: frontend built in, served by FastAPI
backend/
  main.py           — FastAPI app: JSON API + Postgres (SQLAlchemy), CORS for dev
  requirements.txt  — Python dependencies
  Dockerfile        — dev container build for the backend
  .env.example      — copy to .env for secrets/config
frontend/
  src/App.jsx       — React app (API_BASE constant points at the backend)
  src/main.jsx      — entry point, imports Bootstrap CSS + JS
  src/index.css     — custom styles on top of Bootstrap
  vite.config.js    — dev server pinned to port 3001
```

## Run (two terminals, Docker must be running)

```sh
./run-backend.sh      # terminal 1 — starts Postgres + backend (builds if needed)
./run-frontend.sh     # terminal 2 — starts Vite dev server (npm install if needed)
```

Then open http://127.0.0.1:3001. The demo creates, lists, and deletes items
through the API, stored in Postgres.

Notes:

- Backend code hot-reloads inside the container (source is mounted); frontend
  hot-reloads via Vite. No restarts needed while coding.
- The image is only rebuilt when Dockerfile or requirements.txt change;
  force one with `./run-backend.sh --build`.
- Postgres data lives in the `pgdata` Docker volume and survives restarts.
  Wipe it with `docker compose down -v`.
- Both servers listen on 127.0.0.1 only — nothing is exposed to your network.

Interactive API docs (auto-generated by FastAPI): http://127.0.0.1:5001/docs

## Database schema changes (Alembic)

The schema is defined by migration files in `backend/alembic/versions/`, which
are committed to git — so every branch carries exactly the schema its code
expects, and pending migrations apply automatically when the backend starts.

To change the schema:

```sh
./new-migration.sh "add priority column to items"   # creates the file
# edit backend/alembic/versions/<new file>: fill in upgrade() and downgrade()
./migrate.sh                                        # apply now (or just restart the backend)
```

Useful commands:

```sh
./migrate.sh current        # which revision is the DB on?
./migrate.sh history        # list all migrations
./migrate.sh downgrade -1   # roll back the latest migration
```

If a teammate's branch added a migration, it applies on your next backend
start — nothing to do manually.

## Deployment

One container serves everything. The root `Dockerfile` builds the React app
(stage 1) and bakes it into the FastAPI image (stage 2); FastAPI serves the
static files and the API from the same origin, and migrations run on startup.

1. Create a free hosted Postgres (Neon, Supabase, or Render) and copy its URL.
2. Point a Docker-friendly host (Render, Railway, Fly.io) at this repo's root
   Dockerfile and set the env var `DATABASE_URL` to that URL.
3. Deploy — the platform builds the image and gives you one public URL.

Test the production image locally:

```sh
docker build -t hackathon .
docker run --rm -p 8080:5001 -e DATABASE_URL=<your-postgres-url> hackathon
```

## API

- `GET /api/health` — liveness check
- `GET /api/items` — list items
- `POST /api/items` — create an item, JSON body: `{"name": "..."}`
- `DELETE /api/items/{id}` — delete an item

Example:

```sh
curl -X POST http://127.0.0.1:5001/api/items \
  -H 'Content-Type: application/json' \
  -d '{"name": "first item"}'
```
